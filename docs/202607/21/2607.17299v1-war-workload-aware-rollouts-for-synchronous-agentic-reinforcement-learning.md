## 摘要
长序列轨迹生成已成为智能体强化学习（RL）中的主要系统瓶颈。当智能体与环境进行多轮交互时，轨迹迅速增长至数万个token，使得同步RL训练越来越受限于轨迹生成。我们提出WAR，一种工作负载感知的轨迹生成系统，通过联合优化解码与调度，显著加速同步智能体RL。WAR基于一个关键观察：最优轨迹生成优化策略取决于运行时负载：(1) 在低负载下，WAR利用SuffixDecoding实现无模型推测解码，该技术将先前完成轨迹中的后缀模式复用为未来轨迹生成的推测草稿。与基于模型的草稿器不同，SuffixDecoding无需额外草稿模型，避免了与轨迹生成争夺GPU资源。(2) 在高负载下，当饱和的批处理解码使推测加速空间有限时，WAR将优化重点转向缓存感知调度。全局调度器基于缓存局部性、轨迹进度和服务器负载，将请求分配到各轨迹生成副本，从而减少冗余的KV缓存重计算并缓解负载不均衡。通过将解码层面的后缀复用与系统层面的轨迹生成调度相结合，WAR在不同工作负载场景下均能提供稳健的吞吐量提升，且不改变底层RL算法。WAR在低负载下将长上下文智能体轨迹生成吞吐量提升1.4倍，在高负载下最高提升1.6倍。这些结果表明，WAR消除了同步智能体RL中的主要轨迹生成瓶颈，并为可扩展的长上下文智能体训练提供了实用路径。

## Abstract
Long-horizon rollout generation has become the dominant systems bottleneck in agentic reinforcement learning (RL). As agents interact with environments over many turns, trajectories rapidly grow to tens of thousands of tokens, making synchronous RL training increasingly constrained by rollout. We propose WAR, a workload-aware rollout system that substantially accelerates synchronous agentic RL by jointly optimizing decoding and scheduling. WAR is built on a key observation: the optimal rollout optimization strategy depends on runtime load: (1) Under low load, WAR enables model-free speculative decoding with SuffixDecoding, which reuses suffix patterns from previously completed trajectories as speculative drafts for future rollouts. Unlike model-based drafters, SuffixDecoding introduces no additional draft model and avoids GPU contention with rollout generation. (2) Under high load, where saturated batched decoding leaves limited room for speculative speedup, WAR shifts the optimization focus to cache-aware scheduling. A global scheduler places requests across rollout replicas based on cache locality, trajectory progress and server load, reducing redundant KV-cache recomputation and mitigating load imbalance. By combining decoding-level suffix reuse with system-level rollout scheduling, WAR delivers robust throughput improvements across workload regimes without changing the underlying RL algorithm. WAR improves long-context agentic rollout throughput by 1.4x under low load and up to 1.6x under high load. These results show that WAR removes a major rollout bottleneck in synchronous agentic RL and provides a practical path toward scalable long-context agent training.

## 1. 核心问题与整体含义（研究动机和背景）

- **问题**：在同步智能体强化学习（Synchronous Agentic RL）中，长序列轨迹生成（rollout）已成为主要系统瓶颈。智能体与环境多轮交互导致轨迹长度迅速增长至数万 token，而同步训练要求所有轨迹完成后才能更新模型，长尾轨迹（stragglers）导致大量 GPU 空闲，严重制约训练效率。
- **背景**：现有方法要么采用异步 rollout 但引入策略陈旧和分布偏差，要么在同步框架中依赖简单调度（如 least-request + sticky session），未能适应工作负载变化。
- **核心洞察**：最优 rollout 优化策略与运行时负载密切相关：低负载时 GPU 利用率不足，适合推测解码加速；高负载时 GPU 已饱和，调度优化（减少 KV-cache 重计算、负载均衡）更为关键。工作负载应作为一阶因素加以考虑。

## 2. 提出的方法论

### 核心思想
WAR 是一个工作负载感知的 rollout 系统，联合优化解码与调度，根据运行时有效批大小动态切换策略：
- **低负载时**：启用 **SuffixDecoding**（无模型推测解码），复用先前已完成轨迹的后缀模式作为草稿，经目标模型并行验证，加速解码。
- **高负载时**：禁用 SuffixDecoding，转向 **缓存感知调度**，通过全局调度器优化请求在多个 rollout 副本间的放置，以减少冗余 KV-cache 重计算和负载不均衡。

### 关键技术细节
1. **SuffixDecoding**：
   - 基于后缀树缓存历史 token 序列模式，生成时匹配当前 token 序列预测后续 token。
   - 无额外草稿模型，避免 GPU 资源竞争。
   - 支持跨 worker 后缀树同步：每 RL 步后将新轨迹广播到所有 worker 的本地后缀树。
   - 自适应启用/禁用：根据有效批大小动态开关；CUDA Graph 兼容；无状态模式切换。

2. **缓存感知调度**：
   - 当全局请求数 `N_req,tot` 超过阈值 `Thr_sched` 时触发。
   - 对每个排队请求计算总分 `S = Swaiting + Sturn + Scache + Sinflight`：
     - `Swaiting`：基于等待时间，优先防止 sandbox 超时（权重最大）。
     - `Sturn`：根据在线估计的助手回合数（负权重，优先短轨迹以尽早释放 KV-cache）。
     - `Scache`：缓存命中率（正权重，倾向已有缓存的副本）。
     - `Sinflight`：副本上的正在处理请求数（负权重，倾向负载较轻的副本）。
   - 各分量按数量级排序：`|Swaiting| >> |Sturn| >> |Scache| >> |Sinflight|`。
   - 并发控制借鉴 CONCUR 的 AIMD 算法，动态调整每个副本的最大请求数 `W_t`，基于平均缓存命中率 `H_bar` 进行增加/减少/保持，并限制在合理范围内。

3. **工作负载指示器**：使用运行时有效批大小作为轻量级指标，切换阈值根据硬件和任务经验设定。

## 3. 实验设计

- **数据集**：SWE（软件工程）任务数据集，包含 500 个 prompts，每个 prompt 滚动 8 次生成轨迹，最大助手回合数 120。
- **Benchmark**：以 veRL v0.8.0 为基础框架，作为基线。
- **对比方法**：
  - `veRL base`：关闭 WAR 的两个组件，使用 veRL 默认 least-request + sticky session 调度。
  - `sched only`：仅启用缓存感知调度。
  - `spec only`：仅启用 SuffixDecoding。
  - `sched spec`：两者同时启用。
- **消融实验**：
  - 等待因子（`Swaiting`）的存在性影响（batch size 32, 64）。
  - 三个调度因子（`Sturn`, `Scache`, `Sinflight`）单独及组合效果（batch size 16）。
  - SuffixDecoding 的接受长度来源分析（跨提示 vs. 同提示多次 rollout，batch size 4 和 8，rollout n=4 和 8）。
  - 批大小对推测解码吞吐的影响（固定输入/输出长度 8192/512 tokens）。
- **主要指标**：预填充吞吐、解码吞吐、端到端 rollout 时间、缓存命中率、接受长度。
- **工作负载控制**：通过过滤确保不同配置生成的预填充 token、解码 token、助手回合数相对差异均在 5% 以内，以保证公平比较。

## 4. 资源与算力

- **GPU**：16 块 NVIDIA H100（2 节点，每节点 8 块），InfiniBand 互联。
- **模型**：Qwen3-32B，使用 YaRN 扩展支持 96K 上下文长度。
- **并行配置**：训练侧 TP=4, PP=2, CP=2；rollout 侧 TP=4。
- **实验规模**：训练 batch size 从 4 到 64（4,8,16,32,64），每组运行 5 个训练步，每个配置重复并取均值。总实验数约 5×4=20 组（不含消融），消融实验额外若干组。

## 6. 主要结论与发现

- **性能提升**：WAR 在低负载下提升 rollout 吞吐 1.4×，高负载下最高 1.6×（相对 veRL base）。
- **组件互补性**：
  - `sched only`：随负载增加增益增大（预填充吞吐 +0%→+47%，解码吞吐 -4%→+47%）。
  - `spec only`：随负载增加增益减小（预填充吞吐 +53%→+5%，解码吞吐 +48%→+5%）。
  - `sched spec`：在全负载范围保持增益（预填充 +35%→+63%，解码 +32%→+63%）。
- **缓存命中率**：高负载下，启用缓存调度后维持约 0.5，而基线仅 0.1。
- **接受长度**：SuffixDecoding 接受长度约 2.8（低负载）至 6.0（高负载），但高负载下推测解码仍因验证开销而不及纯批解码。
- **来源**：接受长度收益来自跨提示相似性和同提示多次 rollouts 的局部重复模式。

## 7. 优点

- **创新性**：首次将“工作负载”作为一阶因素引入 rollout 优化，提出负载感知的联合解码-调度框架。
- **实用性强**：无需修改底层 RL 算法，兼容现有同步 pipeline（基于 veRL 实现，仅增加轻量控制路径）。
- **无额外模型开销**：采用 SuffixDecoding 避免模型草稿器的 GPU 争用和参数同步问题。
- **智能切换**：自适应启用/禁用推测解码，避免高负载下的负收益。
- **实验设计严谨**：通过工作量过滤、多次运行、误差条报告，确保了结果的可靠性和公平性。
- **消融深入**：不仅评估最终性能，还通过缓存命中率、接受长度等剖析机制，验证了设计直觉。
